Producing robust programs

A robust program keeps working whatever users throw at it, and is easy for other programmers to understand and fix. This topic covers designing programs defensively, and testing them properly.

2.3.1

Defensive design

Defensive design means planning for things going wrong, so the program doesn't crash or produce wrong results and can't easily be misused.

Anticipating misuse

Programmers think about everything a user might do — by accident or on purpose — and make sure the program copes:

  • Typing text where a number is expected, or leaving a box empty
  • Entering very large, negative or very long values
  • Trying to guess passwords again and again
  • Typing code into input boxes, as in an SQL injection attack

The program should check input, show a helpful message and let the user try again, rather than crashing.

Authentication

Authentication is confirming the identity of a user before giving them access — usually with a username and password. It can be made stronger with:

  • rules for strong passwords
  • locking the account after a number of failed attempts
  • two-factor authentication (e.g. a code sent to a phone)
  • biometrics such as a fingerprint or face scan
2.3.1

Input validation

Validation checks that input data is sensible and follows the rules before the program uses it. If it doesn't, the data is rejected and the user is asked to enter it again.

Presence checkSomething has been entered — the field isn't empty
Type checkThe data is the right data type, e.g. a whole number, not text
Range checkA number is between a lower and upper limit, e.g. an age from 11 to 18
Length checkText has an acceptable number of characters, e.g. a password of at least 8
Format checkData follows a pattern, e.g. a postcode, or an email address containing an @
age = int(input("Enter your age"))
while age < 11 OR age > 18
    print("Age must be from 11 to 18")
    age = int(input("Enter your age"))
endwhile

Try it: validation checker

Pick a field, type something in, and see which checks it passes.

    Common mistake

    Validation doesn't check that data is correct — only that it's reasonable. An age of 14 passes a range check even if the person is really 15.

    Going further · grades 8–9

    Verification is different: it checks data has been entered or copied accurately, e.g. typing a new password twice (double entry), or proofreading against the original. Validation and verification together reduce errors, but neither can guarantee the data is true.

    2.3.1

    Maintainability

    Programs are changed and fixed for years after they're written, often by different people. Maintainable code is easy to read, understand and update.

    SubprogramsSplit code into functions and procedures, each doing one job. Easier to read, test and reuse, and a fix only needs making once.
    Naming conventionsUse meaningful names for variables and subprograms (totalScore, not x) in a consistent style, so it's clear what each one holds or does.
    IndentationIndent code inside selection, loops and subprograms so the structure is easy to see — which lines belong to which block.
    CommentsNotes in the code that explain what it does and why. They're ignored by the computer.

    Try it: make it maintainable

    // Works out the cost of a ticket order,
// with 10% off orders over £100
const PRICE = 4.5
const DISCOUNT_LIMIT = 100

function orderCost(numTickets, price)
    cost = numTickets * price
    if cost > DISCOUNT_LIMIT then
        cost = cost * 0.9    // apply 10% discount
    endif
    return cost
endfunction

tickets = int(input("How many tickets?"))
print(orderCost(tickets, PRICE))
    • Comments explain the purpose and the discount
    • Meaningful names: orderCost, numTickets, cost instead of c, a, x
    • Indentation shows what's inside the function and the if
    • Constants for the price and limit — easy to change in one place
    • A clear input prompt for the user
    2.3.2

    Testing

    Programs are tested to find and fix errors, check the program meets its requirements, and make sure it doesn't crash with unexpected input.

    Iterative testingTesting during development: each part (module) is tested as it's written, errors are fixed, and it's tested again — repeated many times.
    Final (terminal) testingTesting the whole program at the end of development, to check all the parts work together and the program meets all its requirements. Often done by, or with, the users.

    Types of error

    Syntax errorBreaks the rules (grammar) of the language, so the program won't translate or run. Example: print("Hello" (missing bracket), whle instead of while.
    Logic errorThe program runs but does the wrong thing. Example: if age > 18 when 18-year-olds should be allowed (should be >=).

    After testing, programmers refine the algorithm: fixing the errors found, and making the program more efficient or more robust.

    Common mistake

    Logic errors are harder to find than syntax errors, because the program runs without an error message. That's why trace tables and good test data matter.

    2.3.2

    Test data and test plans

    Good testing uses four kinds of test data. For an input that should accept whole numbers from 1 to 10:

    NormalTypical data that should be accepted: e.g. 5
    BoundaryData at the very edge of what's allowed, which should be accepted: 1 and 10. Testers also try values just outside (0 and 11), which should be rejected, to check the limits are in exactly the right place.
    InvalidThe right data type but outside the allowed range, so it should be rejected: e.g. 25, -3
    ErroneousThe wrong data type altogether, so it should be rejected: e.g. "seven", 4.5
