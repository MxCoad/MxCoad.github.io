Databases

How relational databases are designed, normalised and queried, and how they keep data correct when many people use them at once. The SQL playground runs real queries on a small school database.

1.3.2a

Relational databases, keys and ERDs

A flat file database stores everything in a single table. That leads to data redundancy (the same data repeated), which wastes space and causes inconsistency when one copy is updated and another isn't.

A relational database splits data into separate tables (one per entity), linked by keys. Each fact is stored once.

EntityA thing about which data is stored, e.g. Student, Course. Each becomes a table.
Primary keyA field that uniquely identifies each record in a table, e.g. StudentID.
Composite keyA primary key made of two or more fields combined, e.g. (StudentID, CourseID) in Enrolment.
Foreign keyA field in one table that is the primary key of another table, used to create the link (relationship) between them.
Secondary keyA field that is indexed so records can be searched or sorted quickly by it, though it is not unique, e.g. Surname.
IndexA separate structure listing key values and where each record is stored, so the database doesn't have to search every record. It speeds up searching but uses extra storage and slows down inserts and updates.

Entity relationship diagrams

Relationships are one-to-one, one-to-many or many-to-many. The "many" end is drawn with a crow's foot. A many-to-many relationship can't be built directly, so it is broken into two one-to-many relationships with a link table:

One student has many enrolments, one course has many enrolments, so students and courses are many-to-many through Enrolment. Enrolment holds StudentID and CourseID as foreign keys, and together they form its composite primary key.

1.3.2b

Normalisation

Normalisation is the process of organising tables to remove redundancy and avoid problems when adding, updating or deleting data. You need to know three normal forms:

First normal form (1NF)No repeating groups of attributes; every field holds a single (atomic) value; each record has a primary key.
Second normal form (2NF)In 1NF and no partial dependencies: every non-key field depends on the whole primary key, not just part of a composite key.
Third normal form (3NF)In 2NF and no transitive (non-key) dependencies: non-key fields depend only on the key, not on other non-key fields. "The key, the whole key, and nothing but the key."

Stage

Going further

Normalisation isn't always the end of the story. Joining many tables is slow, so large systems that are mostly read (such as reporting databases) are sometimes deliberately denormalised, accepting some redundancy in exchange for faster queries.

1.3.2c

SQL

SQL (Structured Query Language) is used to define, query and change data in a relational database. You need to read and write:

SELECT Surname, Form          -- fields to show (* = all)
FROM Student                  -- table(s)
WHERE Form = '12A' AND Surname LIKE 'K%'   -- % = any characters
ORDER BY Surname DESC         -- ASC is the default

SELECT Student.FirstName, Enrolment.Grade
FROM Student
INNER JOIN Enrolment ON Student.StudentID = Enrolment.StudentID

INSERT INTO Student (StudentID, FirstName, Surname, Form)
VALUES (7, 'Grace', 'Lee', '12A')

UPDATE Enrolment SET Grade = 'A' WHERE StudentID = 2 AND CourseID = 'CS'

DELETE FROM Enrolment WHERE StudentID = 1

DROP TABLE Enrolment

In the exam

Forgetting the WHERE on an UPDATE or DELETE changes every record. When joining tables, qualify field names that appear in both tables, e.g. Student.StudentID.

1.3.2d

Capturing, selecting, managing and exchanging data

  • Capturing: paper or online forms, OMR (marks on multiple-choice sheets), OCR (scanning printed text), barcodes and QR codes, sensors, card readers. Forms should be designed with validation to keep bad data out.
  • Selecting and managing: queries (SQL or query-by-example) select the data needed; a DBMS (database management system) handles storage, security, backups, indexing and access by many users.
  • Exchanging: data is moved between systems in standard formats such as CSV, XML or JSON, or by EDI (electronic data interchange), where organisations' systems exchange documents such as orders and invoices automatically in an agreed format.
1.3.2e

Integrity, transactions and record locking

Referential integrity means every foreign key value must match an existing primary key value in the linked table. The DBMS will refuse to add an enrolment for a student who doesn't exist, or to delete a student who still has enrolments (or will cascade the delete to them). Transaction processing and ACID

A transaction is a single logical operation, which might involve several changes, e.g. moving money takes it from one account and adds it to another. Transactions must have the ACID properties:

AtomicityA transaction is all or nothing: either every change happens, or none do (it is rolled back).
ConsistencyA transaction takes the database from one valid state to another; no rules (such as referential integrity) are broken.
IsolationTransactions running at the same time give the same result as if they ran one after another; they don't interfere.
DurabilityOnce a transaction is committed, it stays saved, even if there is a power cut or crash straight afterwards (it is written to secondary storage).

Record locking

If two users read the same record, change it and save it, one update is lost. Record locking stops this: while one transaction is using a record, it is locked and other transactions must wait. A risk is deadlock: transaction 1 has locked record A and is waiting for B, while transaction 2 has locked B and is waiting for A, so neither can continue. (Alternatives include serialisation, timestamp ordering and commitment ordering, which make concurrent transactions behave as if run one at a time.)

Redundancy

Here, redundancy means something good: keeping duplicate copies of the database on separate hardware, often in another place, so the system keeps running if one fails. This is different from data redundancy inside tables, which normalisation removes.

Common mistake

Don't explain record locking as "stopping two people from seeing the data". It stops the same record being changed by two transactions at once, which would lose an update.
