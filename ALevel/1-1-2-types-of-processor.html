Types of processor

Two different philosophies for designing an instruction set, the graphics processor and why it's now used for far more than graphics, and how multicore and parallel systems speed things up — and where they stop helping.

1.1.2a

CISC and RISC

A processor's instruction set is the full list of machine code instructions it understands. There are two approaches to designing one.

CISC — Complex Instruction Set ComputerRISC — Reduced Instruction Set Computer
InstructionsA large set, including complex instructions that do several things (e.g. load, multiply and store in one)A small set of simple instructions
Cycles per instructionComplex instructions take several clock cyclesMost instructions take one clock cycle
Instruction lengthVariableFixed — which makes pipelining easier
Program sizeFewer instructions per program, so less RAM for code; easier to write in assemblyMore instructions per program; the compiler has to do more work
HardwareMore complex circuitry, more transistors, more power and heatSimpler circuitry, fewer transistors, less power and heat, cheaper; room for more registers
Typical useDesktop and laptop PCs (Intel and AMD x86)Phones, tablets, embedded systems (ARM) — and increasingly laptops

Try it: the same task, two instruction sets

Multiply the numbers stored at memory locations 200 and 201, and store the answer back in 200.

CISC

MULT 200, 201

1 instruction, but it takes about 4 clock cycles inside the processor (load, load, multiply, store).

RISC

LOAD  R1, 200
LOAD  R2, 201
MUL   R1, R2
STORE R1, 200

4 instructions, 1 clock cycle each — and each one can be pipelined.

Illustrative instruction sets. The point: CISC moves complexity into the hardware; RISC moves it into the compiler and the program.

Which one is it?

Common mistake

RISC isn't "slower because it needs more instructions". Each instruction is so quick and easy to pipeline that RISC processors can be just as fast, while using less power.

1.1.2b

GPUs and their uses

A GPU (graphics processing unit) is a co-processor with hundreds or thousands of simple cores. It's designed to perform the same operation on many pieces of data at once — this is called SIMD (single instruction, multiple data).

That's exactly what graphics needs: to draw a frame, the same calculations (position, lighting, colour) are done for millions of pixels and vertices independently. A CPU with a few powerful cores would have to work through them a few at a time.

Uses beyond graphics

  • Machine learning — training neural networks is mostly huge numbers of matrix multiplications
  • Scientific modelling — weather, climate, protein folding and physics simulations
  • Video editing and encoding
  • Cryptocurrency mining and password cracking — trying many hashes in parallel
  • Financial modelling — running many scenarios at once

A GPU is not a replacement for the CPU. Its cores are simpler and slower individually, and it's poor at tasks that are sequential or full of branches (decisions), which the CPU handles well. The CPU runs the program and hands the parallel work to the GPU.

In the exam

Explain why a GPU suits a task: the task can be split into many independent parts that need the same operation, which the GPU's many cores perform in parallel.

1.1.2c

Multicore and parallel systems

A multicore processor has two or more independent cores on one chip, each with its own ALU, control unit and registers (and usually its own L1 cache). Parallel processing means using several processors or cores to carry out different parts of a task at the same time.

  • SIMD — one instruction applied to many data items at once (GPUs, vector instructions)
  • MIMD — multiple instructions on multiple data: each core runs its own instructions on its own data (multicore CPUs, clusters of computers)

Benefits and limits

Benefits

  • More instructions processed per second
  • Several programs (or threads) can genuinely run at once
  • Large tasks that split well finish much faster

Limits

  • Software must be written to be parallel (split into threads)
  • Some tasks are inherently sequential: each step needs the previous result
  • Overheads: splitting the task, communicating and combining results, keeping caches consistent
  • Cores share RAM and the buses, which can become a bottleneck

Try it: how much faster with more cores?

Choose how much of a task can run in parallel, and how many cores to use. The dashed line is the "perfect" speed-up you might expect.

Speed-up:

Uses Amdahl's law: speed-up = 1 ÷ ((1 − P) + P ÷ N), where P is the parallel fraction and N the number of cores. It ignores overheads, so real speed-ups are lower still. Both axes double at each gridline.

Going further

This is Amdahl's law: the sequential part of a task sets a hard limit. If 10% must run in sequence, the maximum speed-up is 10×, however many cores you add. It's why GPUs are given only the parts of a program that are almost entirely parallel.
