Compression, encryption and hashing

Three ways of transforming data: making it smaller, making it secret, and producing a fingerprint of it. Try the tools to see each technique working on real data.

1.3.1a

Lossy and lossless compression

Compression reduces file size, so files take less storage and transfer faster using less bandwidth.

LossyPermanently removes data, choosing what people are least likely to notice — sounds outside the range of human hearing or masked by louder ones, fine colour detail in images. The original cannot be reconstructed. Much smaller files. JPEG, MP3, MP4. Unsuitable where every bit matters (text, code, medical images).
LosslessReduces size by finding patterns and redundancy and storing them more efficiently. The original can be restored exactly. Less reduction. PNG, ZIP, FLAC. Essential for text, program files and data.
1.3.1b

Run length encoding and dictionary coding

Run length encoding (RLE)

Replaces runs of the same value with the value and the number of times it repeats: WWWWWWBBBW → 6W3B1W. Very effective for data with long runs, such as simple images with large blocks of colour. With little repetition it can make the data bigger, because every single value gains a count.

Dictionary coding

Builds a dictionary of repeated sequences (e.g. words) and replaces each occurrence with a short reference (an index) to its entry. The dictionary must be stored or sent with the compressed data so it can be decoded. Works best when long sequences repeat many times. (Methods such as LZW build the dictionary as they go.)

1.3.1c

Symmetric and asymmetric encryption

Encryption scrambles plaintext into ciphertext using an algorithm and a key, so that anyone who intercepts it can't understand it without the right key.

Symmetric

  • The same key encrypts and decrypts
  • ✓ Fast, so good for large amounts of data (e.g. AES)
  • ✗ Key exchange problem: both sides need the key, and if it's intercepted while being shared, the attacker can read everything

Asymmetric (public key)

  • Each person has a pair of keys: a public key anyone can have, and a private key kept secret. They're mathematically linked
  • Data encrypted with someone's public key can only be decrypted with their private key
  • ✓ No secret key needs to be shared
  • ✗ Much slower (e.g. RSA)

In practice both are used together: HTTPS uses asymmetric encryption to share a symmetric session key safely, then switches to fast symmetric encryption for the data.

Digital signatures

To prove a message really came from Alice and hasn't been changed: Alice hashes the message and encrypts the hash with her private key — that's the signature. Bob decrypts it with Alice's public key and compares it with his own hash of the message. If they match, only Alice could have sent it (only she has her private key), and it hasn't been altered.

Common mistake

To send someone a secret, encrypt with their public key. To sign something, encrypt (the hash) with your private key. Mixing these up is the most common error.

1.3.1d

Hashing

A hash function turns any input into a fixed-length value (the hash or digest). A good hash function is:

  • One-way — you can't work out the input from the hash
  • Deterministic — the same input always gives the same hash
  • Sensitive — a tiny change to the input gives a completely different hash
  • Unlikely to produce collisions (two inputs with the same hash)

Uses

  • Storing passwords: the system stores only the hash (usually with a random salt added). At log-in, it hashes what you type and compares. If the database is stolen, the passwords themselves aren't revealed.
  • Checking integrity: a download's published hash lets you check the file hasn't been corrupted or tampered with.
  • Digital signatures: the hash of a message is what gets signed.
  • Hash tables: hashing a key gives the position to store or find data quickly (see 1.4.2).

Going further

Why salt? Attackers keep rainbow tables: huge precomputed lists of the hashes of common passwords. Adding a random salt to each password before hashing means two users with the same password get different hashes, and a precomputed table is useless. Password hashes such as bcrypt are also deliberately slow, so trying billions of guesses takes far longer.

Common mistake

Hashing is not encryption. Encrypted data is meant to be decrypted with a key; a hash can't be reversed at all.
